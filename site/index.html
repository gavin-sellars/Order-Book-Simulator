A limit order book that replays a full day of Nasdaq

OrderBookSim is a price-time priority matching engine and market simulator. It rebuilds every stock's order-by-order book from a 29.4 GB exchange file, allocates nothing after startup, and is checked message by message against a deliberately simple reference book.

How it works

The decisions behind the speed, and the code for each

Every excerpt below is copied verbatim from the repository at commit 1a7894b. The file name above each one opens those exact lines on GitHub.

obs.core.OrderPool

Orders are slots in arrays, not objects

An order is an int index into seven parallel arrays. Free slots are chained through the same next array the price-level queues use, so taking or returning a slot is a couple of array writes.

The pool never grows. A mid-run resize would be a latency spike, so it fails loudly instead. Its size turned out to matter a lot: with a worst-case 1M-order pool, the id map outgrows the 16 MB L3 cache and synthetic replay drops from 25.6M to 15.6M msg/s.

obs.core.OrderBook

Cancelling from the middle of a queue is O(1)

Cancels are the most common message in a real feed. Each price level is a doubly linked list threaded through the pool, so removing an order means relinking its neighbours. There's no scan and no node object.

If that empties the best level, a bitset of non-empty levels finds the next one, 64 levels per machine word. Across a 10,000-level gap that is 12.8× faster than stepping one level at a time. The linear scan is still in the code as an option so the difference stays measurable.

From a 1,000-order queue: 30.9 ns against 268.1 ns for the reference book's ArrayDeque.remove.

obs.mem.LongIntMap

Order ids map to slots without boxing

A HashMap<Long, Integer> allocates 96 bytes for every add and remove. This map is two flat arrays with linear probing, sized to a power of two so the modulo becomes a single AND.

Two details were measured, not assumed:

  • Deletion shifts entries back instead of leaving tombstones, so probe chains stay short with no rehashing.
  • Keys go through MurmurHash3's finalizer first. Exchange order ids are sequential, and without the mix a run of live ids forms one long cluster: removals got about 2,200× slower.
obs.core.OrderBook

Matching walks the ladder by array index

Prices are integers with four implied decimals, and a price level's position is (price − base) / tick. Crossing the spread compares array indexes and takes orders from the head of each level's queue, which is what price-time priority means.

The book has two entry modes. Matching mode (addLimitOrder) runs this loop. Book-builder mode applies an exchange feed's own executions, because a feed has already been matched and re-matching would double-count trades.

real data

Real data forced one redesign

A flat array of price levels only works while prices stay near the market. On the real file, every busy stock had resting orders from $0.0001 to $199,999: exchange stub quotes. A ladder covering that would be about 2 billion levels.

The ladder became a window around where the stock trades. Anything outside it goes to a small per-side array of "far levels" kept sorted by price, which reuse the same pool links, so cancels and executions work unchanged.

Far orders are 0.001–1.3% of a busy stock's messages. An A/B against the previous commit showed a 3–5% cost on matching micro-benchmarks and no measurable difference on replay.

obs.feed.itch

Reading ITCH without creating objects

The ITCH file is memory-mapped and each field is read at its fixed byte offset straight into a handler call. No message objects are created, so the reader stays inside the zero-allocation budget too.

Every offset is checked against bytes written out by hand from the Nasdaq specification, so the writer and reader can't share the same wrong offset without a test noticing.

obs.sim

Exact queue position from L3 data

To measure what latency costs a strategy, you need to know when its resting order would have filled, and that depends on how many shares were ahead of it in the queue.

Strategy orders never enter the historical book. Each one records the book's arrival sequence number when it joined. Every real order with a lower number was ahead of it. When one of those trades or cancels, the strategy order moves up. When an order behind it trades, the strategy order must have been reached first, so it fills.

Correctness

A slow, obviously correct book checks the fast one

The fast book's data structures make bugs easy to write and hard to see. So every test compares it against RefOrderBook, which is written for clarity rather than speed, and fails on the first message where they disagree.

Property-based differential tests

jqwik generates thousands of random sessions, including invalid input. After every message, both books must agree on the result, every trade and the full depth. Failures shrink to a minimal reproduction.

Real data, message by message

Seven busy Nasdaq stocks replayed side by side: 86.4M order messages, 0 mismatches, 0 unknown orders, and every book empty at the close.

The whole market

All 909,958,826 order messages for 12,119 stocks applied to one fast book per stock: 0 rejected, every book structurally valid at the end.

Planted bugs

Copies of the project with a touch bug, a reduce bug and blank-slot map deletion were each caught by the suite, which shows the tests can fail.

Structural invariants

BookValidator walks links, cached totals, the bitset, time priority and pool/map agreement after every message in tests.

Zero allocation as a test

The JVM's per-thread allocation counter must not move across a million-message replay. There is also a 200M-message run under the no-op Epsilon GC.

The differential loop

One random session goes to three books: the fast book, the reference book, and a variant of the reference book with O(1) cancel, which is kept to measure what each optimisation buys.

The step label in every assertion makes a failure readable: which message, what it was, and which ids it resolved to.

Proving zero allocation

A zero-allocation claim is easy to make and easy to break later. This test runs on every build. A second test checks that the reference book does allocate, so a broken measurement that always reads zero would fail.

Where it loses

What the design costs, measured

A design only makes sense next to what it gives up. These were all measured.

  • The lead only exists while the working set fits in cache.With a worst-case 1M-order pool, a TreeMap book with O(1) cancel beats it. Across the whole market, 2.1 GB of books make each message 4–7× slower than a single-stock replay.
  • Get the pool size wrong and three of four single operations invert.At 1,048,576 orders, add-then-cancel takes 85.3 ns against the reference book's 46.4.
  • A fill touches seven separate arrays.Struct-of-arrays costs cache lines exactly where matching needs them.
  • The ladder window is fixed for the day.It is sized from the day's own trading range, which a live system wouldn't know in advance. A live system would need to re-centre it.
  • Two threads didn't help.A parse-thread/book-thread pipeline over a lock-free ring buffer was built and measured: no faster for file replay, because parsing is too cheap to offload.
  • The simulator has no market impact.Historical orders still trade after the strategy took their liquidity. That's tolerable for small orders and wrong for large ones.

How it was built

Process

The build followed a written design guide (order-book-guide.md), with Claude Code as a pair programmer; the commits are co-authored. IMPLEMENTATION_PLAN.md records each milestone, the bugs found in the guide's own code, and every place the build departed from the plan.

After the first version, an audit of the benchmarks found flaws that were fixed and re-measured, and running real Nasdaq data forced the far-level redesign. Both are in the history.

Run it

Three commands

You need JDK 25. The Gradle wrapper downloads everything else. On Windows, use gradlew.bat.

./gradlew build          # compile and run all 234 tests
./gradlew itchSession    # generate a synthetic day as ITCH, replay it, check every event
./gradlew latencySweep   # the sample market maker at 0 µs to 50 ms of latency

For real data, download a TotalView-ITCH 5.0 day from Nasdaq and follow the README.
